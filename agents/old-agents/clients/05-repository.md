# Agent 05 — Repository Implementation

## Objective

Implement the repository layer for the Clients Service.

This agent owns the persistence abstraction that sits between sqlc and the business services.

The repository layer is responsible only for data persistence and retrieval.

It must not contain business rules.

It must not contain OAuth logic.

It must not contain webhook logic.

It must not contain gRPC logic.

It must not contain runtime wiring.

The repository should mirror the architecture used by the Deposits service wherever applicable.

---

# Architecture Requirements

Repositories should:

depend on sqlc

hide SQL implementation

return domain models where appropriate

accept context.Context

wrap persistence errors

remain deterministic

be easily mockable

Avoid leaking sqlc-specific implementation into future service layers.

---

# Constructors

Create constructors matching the Deposits service conventions.

Repository constructors should receive:

database pool

logger (if used by Deposits)

generated sqlc queries

Do not construct dependencies internally.

Everything should be dependency injected.

---

# CRUD Operations

Implement repository methods for:

Create

Update

Delete

FindByID

List

Exists

Count

Lookup by external identifiers

Lookup by client

Lookup by platform

Support pagination where required.

---

# Transactions

Implement transaction support where multiple persistence operations must occur atomically.

Reuse the transaction style already established by Deposits.

Do not implement business transactions.

Only repository/database transactions.

---

# Error Handling

Follow existing repository conventions.

Wrap errors consistently.

Avoid returning raw PostgreSQL errors.

Differentiate:

not found

duplicate

constraint violations

connection failures

without exposing SQL implementation details.

---

# Logging

If the Deposits repository logs database operations, mirror the same approach.

Do not introduce excessive logging.

Never log:

OAuth tokens

refresh tokens

provider secrets

encrypted payloads

client secrets

---

# Repository Interfaces

Ensure repository interfaces remain small.

Avoid "god interfaces."

Split responsibilities by aggregate where appropriate.

Repositories should be independently mockable.

---

# Dependency Rules

Repositories may depend on:

database

sqlc

logger

standard library

They must not depend on:

gRPC

protobuf

OAuth providers

HTTP clients

service implementations

runtime packages
