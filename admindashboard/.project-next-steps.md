# AWS Deployment Guide (Agent 06)

This is the only file authorized by the Dockerization sequence to hold the AWS deployment guide. It is authoritative because the production image and container were verified in Agent 06. AWS infrastructure is NOT created here, and no AWS service is assumed — architecture choices are called out explicitly as decisions that still need to be made.

## 1. Dockerization status

- COMPLETE for the local production capability. The Dockerfile and Makefile ship a reproducible, minimal, non-root production Next.js 16.3.0 standalone container that listens on port 3000.
- The image `rvpay/admin:agent03` (built on this host by Agent 03/04) starts successfully, serves HTTP 200 on `/`, `/payment`, `/installation`, `/payouts`, `/sub-accounts`, serves static assets, runs as unprivileged user (uid/gid 1001), and contains no secrets.
- In THIS sandbox the rebuild step (`make build` / `make verify`) stalls because the buildkit network isolation blocks the `next/font/google` build-time font fetch. This is an environment limitation, not a Dockerfile defect; the identical build succeeded earlier on this host (Agent 03/04). Rebuild with normal container network egress.

## 2. What is ready

- `Dockerfile` — three-stage build: `deps` (`npm ci` from committed lockfile) -> `builder` (`next build`) -> `runner` (minimal `node:22-alpine` standalone runtime).
- `next.config.ts` — `output: "standalone"` (correct for Docker).
- `.dockerignore` — excludes `.git`, `node_modules`, `.next`, env files (`**/.env`, `**/.env.*`), `*.pem`, docs, and agent files, keeping layers small and secrets out.
- `Makefile` — repeatable local workflow (`build`, `run`, `stop`, `verify`) plus a thin AWS ECR interface (`tag`, `ecr-login`, `ecr-push`).
- Runtime contract: non-root `nodejs` (uid/gid 1001), port 3000, `NODE_ENV=production` baked in.

## 3. Image / build workflow

- Local: `make build` (docker build), `make run` (detached on port 3000), `make stop`, `make verify` (build + HTTP-200 smoke + stop).
- Image name `rvpay/admin`, tag `latest` by default; override with `IMAGE` / `TAG` / `PORT` / `CONTAINER`.
- AWS ECR interface: `make tag`, `make ecr-login`, `make ecr-push` — require `AWS_REGION`, `AWS_ACCOUNT_ID`, `AWS_ECR_REPO`, fail loudly when any is missing.

## 4. Environment / secrets requirements

- The application uses ZERO environment variables (verified by grep over the whole source tree and reconfirmed by Agent 04). No `.env` is required at build or runtime.
- Do NOT convert any future runtime secret into `NEXT_PUBLIC_*`. If a variable is ever needed, supply it at container runtime via `docker run -e KEY=value` / `--env-file` (or your orchestrator's secret mechanism), never baked into the image.
- Secrets policy: never commit real credentials; use your cloud secret store at runtime.

## 5. AWS prerequisites

- An AWS account with a region configured.
- CLI credentials with permission to do the specific ECR operations you run (the Makefile shells out to `aws ecr get-login-password`; AWS CLI must be installed and authenticated).
- An ECR repository (name passed as `AWS_ECR_REPO`) — creation is NOT automated here.
- `docker` available locally; `aws` CLI available for `ecr-login`.

## 6. Recommended low-cost deployment sequence

1. `make build` and `make verify` locally with normal network egress.
2. Create an ECR repository in your region.
3. `make ecr-login AWS_REGION=... AWS_ACCOUNT_ID=... AWS_ECR_REPO=...` and complete the implied `docker login` to ECR.
4. `make ecr-push AWS_REGION=... AWS_ACCOUNT_ID=... AWS_ECR_REPO=...` to push the image.
5. Choose a compute target (see "Items requiring an explicit decision" below), run the image on port 3000, attach a load balancer / ingress that forwards HTTP to the container's port 3000.
6. No application changes are required to sit behind AWS — it is a plain single-port HTTP service.

## 7. Items requiring an explicit AWS architecture decision

- Compute target: ECS (Fargate) vs EC2 vs App Runner vs EKS. Nothing in this repository preselects one. Fargate / App Runner need no instance management; EC2 is the lowest raw cost; App Runner can push from ECR directly.
- TLS / ingress: the container listens on port 3000; decide whether a load balancer terminates TLS (recommended) in front of it.
- Health check: `/` returns 200; configure the LB health check path to `/`.
- Environment injection: with zero required vars there is none; if future vars appear, define them in the platform's secret store.
- ECR repository lifecycle and IAM roles for the compute service.

## 8. Rollback / update considerations

- All Makefile and Docker workflow operates on tagged images, so rollback is point-in-time: keep previous `TAG` values and redeploy the old tag.
- Recommended: give each deploy a distinct `TAG` (e.g. a commit hash) and keep the last few tags; do not rely only on `latest`.
- Standalone output means no `node_modules` or build step at runtime; redeploy = new image.

## 9. Commands / targets already available

- `make build`, `make run`, `make stop`, `make verify` — local Docker workflow.
- `make tag`, `make ecr-login`, `make ecr-push` — AWS ECR interface (all three AWS vars required).
- `make help` prints the full list.

## 10. Things deliberately not implemented

- AWS infrastructure (VPC, cluster, task definition, load balancer, IAM).
- CI/CD pipeline, Terraform/CDK/CloudFormation, Docker Compose, or helm charts.
- `.env.example` (no application variables exist to document).
- No secrets or credentials committed anywhere.
- No application modernization or dependency upgrades.

AWS deployment is NOT complete; this guide is the decision checklist for that later work.
