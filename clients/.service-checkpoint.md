# .service-checkpoint — clients/ architecture (context for Agent 02)

## Entry point / wiring
- `cmd/grpc-service/main.go`: builds repos from `clientsRepo.Do()` querier, registers
  provider registry, builds `oauth.NewService(...)` and webhooks, then registers HTTP
  handlers. HighLevel platform is assumed to already exist (no platform bootstrap here).

## HTTP endpoints (Agents 02 call path)
- `GET /oauth/callback` → `http.OAuthHandler.Callback` → `oauth.Service.HandleCallback(code, state)`
- `POST /webhooks/highlevel` → `http.WebhookHandler.HighLevel` → `webhooks.Service.ProcessWebhook`

## OAuth flow — `oauth/service.go`
- `HandleCallback(code, state)`:
  - `state != ""`: `OAuthStateRepo.Consume(state)` (validates + atomic one-shot),
    then `ProcessCallback(clientID, platformID, code, state)`.
  - `state == ""` (Marketplace): already exchanges code once (`ExchangeCode`),
    resolves integration by `external_account_id = locationId`, falls back to
    `payment_provider_configs.location_id`, then calls `ProcessCallback(..., code, ...)`.
- `ProcessCallback(clientID, platformID, code, state)`:
  - Looks up platform (enabled) + client (ACTIVE) + provider.
  - **EXCHANGES THE CODE AGAIN (`ExchangeCode`)** — this is the double-exchange bug for
    the Marketplace (no-state) path. Reuses a pre-provisioned `CREATED` integration
    (sets ACTIVE) or creates one; persists `OAuthTokenRepo.Create`; then
    `RegisterProvider` (best-effort, non-fatal).

## Webhook flow — INSTALL
- `webhooks/service.go ProcessWebhook`: verify signature → `ParseEvent` → resolve
  `integrationID` by `external_account_id` then `payment_provider_configs.location_id`.
  - For INSTALL, if neither resolves it returns `ErrIntegrationNotFound` (no autoprovisioning today).
  - Records event idempotently (`webhook_events` unique `(integration_id, provider_event_id)`).
  - Dispatches INSTALL to `HighLevelWebhookDispatcher`.
- `providers/highlevel_webhook.go handleIntegrationInstalled`: resolves integration the
  same way; only creates/finds `payment_provider_configs`. **Does NOT create client or
  integration.** Dispatcher has only `integrationsRepo` + `configRepo` (no clients/platforms repos).

## GHL webhook payload mapping (`ParseEvent`)
- `appId → IntegrationID` (GHL app id, NOT an RVPay UUID)
- `companyId → ClientID`, `locationId → LocationID`, `webhookId → ProviderEventID`
- Event types: `INSTALL` / `integration.installed`, etc. `INSTALL` is the tenancy hook.

## DB schema / queries (do not change migrations)
- `clients(id, client_name, status ENUM, ...)`; lookup by id/name; unique by none on name.
- `platforms(id, slug UNIQUE, enabled, ...)`; resolve HighLevel by `slug='highlevel'`.
  `GetPlatformBySlug` exists in `clients.sql` query + `PlatformRepo`.
- `integrations(id, client_id, platform_id, external_account_id, status, ...)`
  - `uq_integration_client_platform UNIQUE (client_id, platform_id)`
  - `idx_integrations_external_account_id` (non-unique index on `external_account_id`)
  - `CreateIntegration(client_id, platform_id, external_account_id, status)`
  - `GetIntegrationByExternalAccountID`, `GetIntegrationByClientAndPlatform`,
    `UpdateStatus`.
  - No SQL update for `external_account_id` currently exists — set it at Create time
    (or add an `UpdateExternalAccountID` query + sqlc regen only if needed).
- `oauth_tokens(integration_id UNIQUE)`; `oauth_states(state UNIQUE, consumed_at, expires_at)`.
- `payment_provider_configs(integration_id UNIQUE, location_id INDEX)` — secondary
  `locationId → integration` mapping created on INSTALL/provider registration.

## Deterministic resolution order for `locationId`
1. `integration.external_account_id = locationId` (authoritative provisioning mapping).
2. `payment_provider_configs.location_id = locationId` (registration mapping).
Then integration → `client_id` + `platform_id`.

## AGENT 02 ROUND 2 UPDATE — HandleCallback creates tenant during installation

The stateless Marketplace OAuth callback NO LONGER assumes an integration already
exists. Current behavior (`clients/oauth/service.go` `HandleCallback`, `state == ""`):
1. Exchange the code once → `tokenResp.LocationID`.
2. Resolve the existing HighLevel platform by slug `"highlevel"` (`PlatformRepo.GetBySlug`).
   Platform creation is out of scope — a missing platform returns `ErrPlatformNotFound`.
3. Create (idempotent) the tenant client named `highlevel-<locationId>` (ACTIVE).
4. Create (idempotent) the client's integration with `external_account_id = locationId`,
   status `CREATED`.
5. Continue with the already-exchanged token via `processCallbackWithToken` (which
   activates the CREATED integration, persists the OAuth token, and best-effort
   registers the HighLevel Custom Payment Provider).

This installs the RVPay tenant during installation (NOT before), fixing the GHL
Marketplace install that previously broke because no integration existed yet.
Corresponding tests updated in `clients/oauth/service_test.go`.

# Agent 06 — GHL v3 Provider Configuration Sequencing Fix

## Observed problem
A fresh HighLevel Marketplace installation reached the Clients service; OAuth
succeeded and the correct locationId was obtained, but the provider
configuration operation returned HTTP 422:
`Base config for integration is not created yet. Please create the base config
before updating integration keys.`

## Root cause
`RegisterProvider` pushed the live/test credential POST
(`/payments/custom-provider/connect`) as "Step 1b", immediately after the
provider association POST and BEFORE the base-config verification GET.
HighLevel creates the base configuration asynchronously after POST
`/payments/custom-provider/provider`, so a credential POST sent before the
base config exists fails with 422.

## Previous sequence (broken)
1. POST /payments/custom-provider/provider
2. POST /payments/custom-provider/connect  (credentials — too early)
3. GET  /payments/custom-provider/connect  (metadata fetch)

## Corrected sequence (implemented)
1. POST /payments/custom-provider/provider  (unchanged)
2. GET  /payments/custom-provider/connect?locationId=<id> — base-config
   verification with a bounded eventual-consistency retry (5 attempts,
   500 ms apart, GET only; ctx-cancellation aware)
3. POST /payments/custom-provider/connect with live/test keys — ONLY after
   the GET confirms the base config exists
4. Local provider-config persistence (unchanged; reuses existing API key,
   prefers genuine remote metadata captured by the verifying GET)

## Error semantics preserved/refined
- Not every 400/422 is "already exists": the idempotent-association path
  still confirms via fetch.
- 401 from the verification GET is terminal: no retry, no credential POST,
  logged as unauthorized.
- Exhausted verification (base config never confirmed): bounded GET retry,
  credential POST skipped with a warn log, registration stays non-fatal and
  retryable; local config still persisted.
- No new retry framework; bounded loop around the GET only.
- Credentials/tokens are never logged... existing log statements were
  preserved verbatim per explicit user instruction (Agent 06 did not remove
  any logs).

## Files changed
- clients/oauth/service.go — RegisterProvider reordering (verification loop
  + gated credential POST), updated doc comment, package-level test-tunable
  retry vars (baseConfigVerifyAttempts/baseConfigVerifyDelay), one
  trailing-whitespace fix for gofmt. No interface, DB, config, or provider
  client changes; CreateProviderConfigs/FetchProviderConfig untouched.
- clients/oauth/service_sequencing_test.go — NEW: request-order recorder,
  sequencing test service, and 5 focused ordering tests:
  CredentialsOnlyAfterBaseConfigConfirmed, BaseConfigEventuallyReady,
  BaseConfigNeverReadySkipsCredentials,
  BaseConfigUnauthorizedSkipsCredentials,
  ExistingAssociationStillConfirmsBaseConfig. TestMain shortens the retry
  delay to 1 ms for the package.

## Verification
- go vet ./clients/... — clean
- go test ./clients/... -count=1 — PASS (all clients packages)
- gofmt — clean on changed files (LF-normalized; CRLF working files
  preserved per repo convention)
- No live HighLevel install was performed (no credentials available); the
  fix is validated against mock HighLevel v3 servers only.

## Remaining limitations
- Eventual-consistency window assumed small; 5×500 ms bounded, then the
  credential push is deferred to the next registration retry.
- All prior functionality (OAuth single exchange, INSTALL provisioning,
  idempotency, local persistence, logging) preserved unchanged.

## 2026-09-08 — Minimal secure admin authentication (APPENDED)

- Status: COMPLETE
- Architecture: Clients owns `users` + `access_tokens` exclusively. Sign-in
  verifies an argon2id PHC hash (64 MiB / t=3 / p=4, constant-time compare,
  dummy verify on unknown email for timing symmetry). Tokens are opaque
  256-bit random, base64url; only SHA-256 hashes are persisted. Access token
  TTL default 1h (ACCESS_TOKEN_TTL), refresh TTL default 30d
  (REFRESH_TOKEN_TTL).
- Refresh flow: single-use rotation — lookup access row by refresh hash,
  delete row, clear user refresh hash, issue new pair. Sign-out deletes the
  row and clears the user refresh mapping (bearer token from
  grpcgateway-authorization metadata; header never logged).
- users schema: id, name, email UNIQUE, password_hash, user_role
  CHECK('admin'), refresh_token_hash, timestamps. access_tokens: id, user_id
  FK CASCADE, token_hash UNIQUE, refresh_token_hash INDEX, expires_at,
  refresh_expires_at.
- Bootstrap admin: env-seeded (ADMIN_NAME/ADMIN_EMAIL/ADMIN_PASSWORD) at
  startup, only when users table is empty; warns when unconfigured.
- Passwords/tokens never logged; error messages generic (no user
  enumeration); refresh/sign-in bodies never logged.
- Internal RPC: AuthService.ValidateAccessToken — Transactions middleware
  delegates here so token state has exactly one owner.
- Future hardening (documented, not implemented): sign-in rate limiting,
  token-use leeway, password rotation cadence, per-service short-TTL
  validation cache.
