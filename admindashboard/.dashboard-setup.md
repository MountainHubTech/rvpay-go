# Dashboard Setup — RVPAY Admin Dashboard (`admindashboard/`)

This document explains exactly how the dashboard works today: every page, every
piece of static (hardcoded) data, and precisely what a server must return to
replace that data with live information. After reading it, anyone should know
how each page will communicate with a backend and in what shape the backend
must answer.

---

## 1. Application Overview

| Fact | Value |
|---|---|
| Framework | Next.js 16.3.0 (App Router), React 19.2.8, TypeScript |
| Styling | Tailwind CSS 4, shadcn/ui components (`components/ui/`), lucide-react icons |
| Charts | recharts |
| Folder | `admindashboard/` |
| Env vars | **Zero** — no `process.env` / `NEXT_PUBLIC_*` anywhere |
| Auth | None — no session, token, or login flow exists |
| Data layer | **None** — all dashboard data is static, defined in `lib/dashboard-data.ts`; only `/payment` and `/healthcheck` touch a network |

### Routes

| Route | File | Type |
|---|---|---|
| `/` | `app/page.tsx` | Dashboard Overview |
| `/sub-accounts` | `app/sub-accounts/page.tsx` | Sub-Accounts table |
| `/payouts` | `app/payouts/page.tsx` | Payouts Overview |
| `/installation` | `app/installation/page.tsx` | CRM integration success card |
| `/payment` | `app/payment/page.tsx` | HighLevel iframe checkout (the only live page) |
| `/healthcheck` | `app/healthcheck/route.tsx` | API route, `GET` → `{ "status": "ok" }` 200 (force-dynamic) |

### Shared chrome

- `layout.tsx` — Geist + Geist Mono fonts, metadata "RVPAY — Payments Monitor".
- `components/dashboard/app-sidebar.tsx` — static nav: Dashboard (`/`),
  Sub-Accounts (`/sub-accounts`), Transactions (**no route** — disabled),
  Payouts (`/payouts`), Disputes & Errors (**no route** — disabled),
  Settings (**no route** — disabled). Footer shows a hardcoded user:
  `Admin User` / `admin@rvpay.com` — a server must supply the authenticated
  identity here (`GET /me` style endpoint: `{ name, email, avatarUrl }`).
- `components/dashboard/topbar.tsx` — global "Search sub-accounts" input and a
  notification bell; both are inert. A server would back these with a
  sub-account search endpoint and a notifications endpoint.
- `components/dashboard/period-select.tsx` — client dropdown with static
  options `["Last 7 Days", "Last 30 Days", "Last 90 Days", "This Year"]`;
  state is local only and **does not drive any data fetch yet**. Server work:
  accept a `period`/`from`/`to` parameter on the overview endpoints.

### The static-data hub

`lib/dashboard-data.ts` is the single module all dashboard widgets import. It
exports typed constants — every dashboard number/table row on the site comes
from here:

- `statCards: StatCard[]`
- `revenueOverTime: { period: string; revenue: number }[]`
- `needsAttention: AttentionItem[]`
- `recentPayouts: Payout[]`
- `subAccounts: SubAccount[]`
- `payoutOverviewStats: PayoutOverviewStat[]`
- `payoutOverviewRows: PayoutOverviewRow[]`

Recommended replacement pattern: turn each export into an API-backed hook
(e.g. `useStats(period)` fetching from a `/api/v1/...` route or the Go
services directly) while keeping the existing TypeScript types as the response
shapes — the components need no UI change if the server returns exactly the
structures below.

## 2. Page-by-Page Specification

### 2.1 `/` — Dashboard Overview (`app/page.tsx`)

Server-rendered layout composed of: `Topbar`, `PeriodSelect`, `StatCards`,
`RevenueChart`, `NeedsAttention`, `RecentPayouts` (inside a shared `AppSidebar`
shell).

#### 2.1.1 Stat Cards — `components/dashboard/stat-cards.tsx`

Renders four cards from `lib/dashboard-data.ts`:

| # | label | static value | extra | icon key |
|---|---|---|---|---|
| 1 | Total Revenue | `$1,245,670.00` | trend: `up`, "+12.5% vs last period" | `revenue` |
| 2 | Transaction Volume | `45,210` | meta: `"4.5k · 510 · 200"` (successful/failed/pending breakdown) | `volume` |
| 3 | Active Sub-Accounts | `1,842` | meta: `"+24 new this week"` | `subAccounts` |
| 4 | Pending Payouts | `$342,100.50` | meta: `"Next payout run tomorrow"` | `payouts` |

**Server contract expected** (values are preformatted display strings,
including currency symbol and trend label — the backend should either return
raw numbers and let the client format, or match these strings exactly):

```
GET /api/v1/overview/stats?period=7d|30d|90d|year
→ [ { label: string, value: string,
      trend?: { direction: "up"|"down", label: string },
      meta?: string, icon: "revenue"|"volume"|"subAccounts"|"payouts" } ]
```
The `PeriodSelect` currently has no wiring; it should supply the `period`
query param and the component should refetch.

#### 2.1.2 Revenue Chart — `components/dashboard/revenue-chart.tsx` (client component)

A recharts `BarChart` fed by `revenueOverTime`:

```
[ { period: "Week 1", revenue: 68000 }, { "Week 2", 92000 }, { "Week 3", 81000 },
  { "Week 4", 118000 }, { "Week 5", 96000 }, { "Week 6", 142000 }, { "Week 7", 168000 } ]
```
Bars are shaded by a static grayscale ramp (`#e5e5e5` → `#262626`) per index.

**Server contract expected:**

```
GET /api/v1/overview/revenue?period=...&granularity=week
→ [ { period: string, revenue: number } ]   // revenue = number (tooltip shows
                                            // raw value); one entry per bucket
                                            // (week/day/month by granularity)
```

#### 2.1.3 Needs Attention — `components/dashboard/needs-attention.tsx`

Renders `needsAttention` items with severity → badge styling:

| severity | badge | static rows |
|---|---|---|
| `dispute` | rose, "DISPUTES" | `att-1` "Arktribe disputed charge $450.00" (2h ago, "View details"); `att-3` "Adna Cards disputed charge $210.00" (1d ago, "View details") |
| `failed-payout` | amber, "FAILED PAYOUT" | `att-2` "Routing error for Applemelon ($1,200)" (5h ago, "Resolve issue") |

Header shows a count badge (`{length} items`). Action buttons are inert — they
must link to detail views/resolution flows the server will expose.

**Server contract expected:**

```
GET /api/v1/overview/needs-attention
→ [ { id: string,
      severity: "dispute" | "failed-payout",
      title: string,               // human-readable, preformatted
      timeAgo: string,             // e.g. "2h ago" (or send timestamp + format client-side)
      actionLabel: string,
      actionHref?: string,         // new — needed to make the button work
      refId?: string } ]           // dispute id / payout id to act on
```

### 2.5 `/payment` — HighLevel Checkout (`app/payment/page.tsx`)

The only page with live server communication. `"use client"` page loaded by
HighLevel as the registered `paymentsUrl` inside an iframe. Flow:

1. **Handshake (postMessage, no server):**
   - Registers a `window.addEventListener("message", ...)` listener **before**
     posting the ready event.
   - Posts `JSON.stringify({ type: "custom_provider_ready", loaded: true,
     addCardOnFileSupported: false })` to `window.parent`, retried every
     **500ms** until the payment context arrives or unmount.
   - Accepts `payment_initiate_props` **and** `setup_initiate_props` events;
     `event.data` may be a JSON string or an object (safe `JSON.parse`,
     malformed ignored). Payload type `PaymentInitiateProps`: `type`,
     `publishableKey`, `amount`, `currency`, `mode`, `productDetails`,
     `contact { id, name, email, contact, shippingAddress }`, `orderId`,
     `transactionId`, `subscriptionId`, `locationId`.
   - Prefills from the event: `amount`, currency → country via
     `CURRENCY_COUNTRY` map (unambiguous ISO codes only; FCFA/XOF/XAF not
     mapped), customer phone (dial code stripped).
   - Extensive `[RVPay]` console diagnostics retained.

2. **Static data on this page (not server-fetched today):**
   - `PROVIDERS` map — 16 pawaPay mobile-money providers with brand colors:
     `mtn` (pill), `orange`, `moov`, `wave`, `airtel`, `vodacom`, `mpesa`,
     `at`, `vodafone`, `tnm`, `movitel`, `free`, `zamtel`, `tigo`, `halotel`,
     `safaricom`.
   - `COUNTRIES` — 20 supported countries (BJ, BF, CM, CI, CD, ET, GA, GH, KE,
     LS, MW, MZ, NG, CG, RW, SN, SL, TZ, UG, ZM), each with flag emoji, dial
     code, display currency and provider list (e.g. GH → GHS → mtn/at/
     vodafone).
   - **Server replacement:** a provider-availability endpoint so the lists
     become dynamic:
     ```
     GET /api/v1/payment/providers?country=GH
     → [ { id: string, name: string, bg: string, fg: string,
           shape?: "pill"|"square" } ]
        // plus per-country availability/currency, sourced from pawaPay
     ```
   - URL query params also read (fallback to the event): `type`,
     `transactionId`, `apiKey`, `chargeId`, `subscriptionId`, `amount`.
     `buyNowProductId` is deliberately NOT treated as a transactionId.

3. **Pay → initiation (server call #1):**
   `POST https://api.rvpay.xyz/v1/public/deposits` (Transactions service,
   grpc-gateway, `CreateDepositRequest`). Body mapping:
   - `clientName = "highlevel-<locationId>"` (backend convention)
   - `customerId = initiateProps.contact.id`
   - `merchantId = payer phone number` (current temporary requirement — NOT
     the HighLevel transactionId)
   - `ghlTransactionId = genuine HighLevel transactionId` (persisted in
     `deposits.ghl_transaction_id` for verify lookups)
   - `amount` (validated positive number), `currency` via `currencyToApi`
     (`FCFA` → `XAF`, else uppercase ISO), `paymentType`,
     `payerPhoneNumber`, `provider` via `providerToApi` — only `mtn` →
     `PROVIDER_MTN_MOMO` and `orange` → `PROVIDER_ORANGE_MOMO` are supported;
     other selections are rejected client-side with "This mobile money
     provider is not supported yet. Please select MTN or Orange Money."
   - Fail-safes before calling: missing `locationId` → "Missing payment
     location information"; missing `contact.id` → "Missing payment contact
     information"; missing `transactionId` → "Missing payment transaction
     information". Terms checkbox + phone + positive amount required to
     enable Pay.
   - Expected success response: the created deposit record (the page retains/
     logs the backend deposit `id`); HTTP 200 is **never** shown as payment
     success.

4. **Status polling (server call #2):**
   `GET https://api.rvpay.xyz/v1/public/payments/verify?ghlTransactionId=...
   [&ghlChargeId=...][&subscriptionId=...]` → `QueryResponse
   { success?: boolean; failed?: boolean; message?: string }`.
   - Polls every **3000ms** (`PAYMENT_POLL_INTERVAL_MS`), single interval.
   - Terminal success: `success === true` → "Payment completed" modal (green ✓).
   - Terminal failure: `failed === true` → "Payment failed" modal (red ✕).
   - Both false → keep polling; transport/server errors logged (`console.warn`)
     and retried inside the window.
   - Hard timeout after **10 minutes** (`PAYMENT_POLL_TIMEOUT_MS`) → timeout
     message, polling stops, result modal NOT shown.
   - Timers cleared on terminal state and unmount; duplicate submissions
     blocked by `isSubmitting`.
   - Modal "OK" dismisses only — no HighLevel return URL exists in the
     integration (documented safe seam for a future `returnTo`).

## 3. Summary — What a Backend Must Provide

| # | Endpoint (suggested) | Replaces | Page |
|---|---|---|---|
| 1 | `GET /overview/stats?period=` | `statCards` | `/` |
| 2 | `GET /overview/revenue?period=&granularity=` | `revenueOverTime` | `/` |
| 3 | `GET /overview/needs-attention` | `needsAttention` | `/` |
| 4 | `GET /payouts/recent?limit=` | `recentPayouts` | `/` |
| 5 | `GET /sub-accounts?search=&status=&sort=` + `POST /sub-accounts` | `subAccounts` + "Add Account" | `/sub-accounts` |
| 6 | `GET /payouts/overview/stats` | `payoutOverviewStats` | `/payouts` |
| 7 | `GET /payouts?search=&status=&page=` (+ `/export`, `/{id}`) | `payoutOverviewRows`, pagination, Export CSV | `/payouts` |
| 8 | `GET /payment/providers?country=` (optional) | `PROVIDERS` + `COUNTRIES` | `/payment` |
| 9 | Identity endpoint for sidebar user (`GET /me`) | hardcoded `admin@rvpay.com` | all |
| 10 | Notifications endpoint (optional) | bell icon | all |

**Existing live endpoints (Transactions service — contract must not change):**
`POST https://api.rvpay.xyz/v1/public/deposits` and
`GET https://api.rvpay.xyz/v1/public/payments/verify`.

**Cross-cutting conventions the server must respect:**
- Return shapes matching the TypeScript types in `lib/dashboard-data.ts` so
  components change minimally (or return raw numbers/timestamps and adopt one
  client-side formatting convention — but be consistent).
- The `PeriodSelect` period must be plumbed through the overview endpoints.
- There is no auth on any route today; whoever adds the server must also
  decide the auth model (sessions/API keys) for the `/api/v1/*` endpoints
  above — none exists client-side.
- No environment variables exist; the API base URL is currently hardcoded to
  `https://api.rvpay.xyz` in `app/payment/page.tsx`. New fetches should follow
  the same convention or introduce one documented `NEXT_PUBLIC_*` variable.
