## Transport / testing
- `NewClient(baseURL, apiKey)` builds an internal `http.Client` (30s timeout), trims a trailing "/" from the base
  URL, and calls `/v2/deposits` / `/v2/payouts` with `Authorization: Bearer <apiKey>`.
- Non-2xx HTTP returns a provider error, so an `httptest.Server` given to `NewClient(srv.URL, "test-key")` is the
  way to test both success and provider-error paths WITHOUT the real API. There is NO mockable interface seam.

## 2026-09-02 — sqlc nullability decision
- Nullable text columns are represented as *string (emit_pointers_for_null_types); the previous override mapping nullable text to plain string was removed because pgx cannot scan SQL NULL into string
- Repository maps absent external identifiers ("") to SQL NULL (textPtr) and passes exact values through for status/reference updates (textRef); converters map NULL to "" only for the protobuf wire contract


## 2026-09-02 — Transaction boundary decision
- InitiateDeposit opens one pgx transaction via TransactionsRepo.Begin; the deposit INSERT runs on repo.NewDepositRepo(txQuerier); PawaPay initiation happens inside the open tx; COMMIT only after PawaPay succeeds, otherwise deferred ROLLBACK. Read paths remain on the pool-backed DepositRepo.


## 2026-09-02 — HighLevel identifier mapping (corrected)
- client_name = "highlevel-<locationId>"
- customer_id = HighLevel contact.id
- merchant_id = payer phone number (temporary/current requirement — NOT the transactionId)
- ghl_transaction_id = HighLevel transactionId, persisted in the existing deposits.ghl_transaction_id column (proto CreateDepositRequest field 8) and used by VerifyPayment for deposit resolution


## 2026-09-02 — PawaPay amount decimals decision
- PawaPay zero-decimal currencies (currently XAF) are serialized with zero decimal places; integrality is validated exactly on the pgtype.Numeric mantissa (Int*10^Exp) — fractional amounts are rejected before the PawaPay call, never rounded or truncated


## 2026-09-02 — PawaPay deposit callback decision
- Endpoint: POST /v1/public/pawapay/deposits/callback (grpc-gateway → PaymentService.ProcessDepositCallback). Unauthenticated by design; must sit behind public HTTPS.
- Correlation: callback depositId == deposits.id (the RVPay UUID supplied at initiation). merchant_id/ghl_transaction_id are never used for callback correlation.
- Status mapping: PawaPay COMPLETED→DepositStatusCOMPLETED (MarkCompleted), FAILED→DepositStatusFAILED (MarkFailed, failure_message preserved in failure_reason), PROCESSING→DepositStatusPROCESSING. providerTransactionId → external_reference.
- Idempotency: terminal states (COMPLETED/FAILED) are final; duplicate same-status callbacks return 200 with no mutation; conflicting late callbacks are logged and ignored with 200 so PawaPay does not retry. Unknown depositId returns 200 (no retry). Missing/invalid fields and unsupported statuses return 400. Repository failures return 500 (retry desirable).
- Signature verification: NOT implemented — pending confirmation that signed callbacks are enabled for the PawaPay account. Do not production-harden until verified; consider an RFC-9421 signature check or an allowlist/IP filter at AWS ALB/API Gateway level in the interim.
