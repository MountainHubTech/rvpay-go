# POC: Fix HighLevel Marketplace First-Install OAuth + Client Resolution

Implement a minimal, production-sensible POC fix for the HighLevel Marketplace installation flow.

IMPORTANT: Do NOT redesign the OAuth system. Do NOT add migrations. Do NOT add External Authentication. Do NOT create fake/default client IDs. Do NOT assume there is only one RVPay client.

## DOMAIN MODEL

- An RVPay Client represents a GHL sub-account/business.
- RVPay Customers are the entities that make payments through that sub-account.
- `clients.id` is an internal UUID generated by the database.
- GHL `companyId`, `locationId`, and `appId` are external identifiers.
- NEVER convert/hash a GHL identifier into an RVPay client UUID.
- NEVER use a random/default client UUID.
- A GHL Marketplace installation MUST resolve to the specific RVPay Client it belongs to.
- Multiple RVPay clients may have HighLevel integrations simultaneously.

## EXISTING POC PROVISIONING

For the POC, the RVPay Client is pre-created before the Marketplace installation.

The existing `InstallIntegration` flow is used to create the HighLevel integration:

    client_id  = existing RVPay client UUID
    platform_id = HighLevel platform ID
    status      = CREATED

The resulting integration is the authoritative client/platform context.

## CRITICAL CLIENT-RESOLUTION REQUIREMENT

The incoming GHL installation MUST NOT simply select an arbitrary HighLevel integration or assume there is only one client.

The implementation must resolve:

    GHL locationId
        ↓
    specific HighLevel integration
        ↓
    integration.client_id
        ↓
    specific RVPay Client

Use the existing schema and fields wherever possible.

In particular, inspect whether `Integration.ExternalAccountID` can safely be used as the GHL location identifier for the pre-provisioned integration.

If the existing schema supports:

    integration.external_account_id = GHL locationId

then use that as the deterministic mapping.

If the existing schema does NOT provide a safe way to establish the first-install mapping from GHL locationId to a specific pre-created RVPay Client, DO NOT guess, select the first client, select the first HighLevel integration, or invent a mapping.

In that case, report the exact blocker instead of implementing an unsafe fallback.

## REQUIRED FLOW

### 1. Existing state-based OAuth flow

Preserve the existing behavior when the callback contains `state`.

Do not break the existing:

    state → oauth_states → clientID/platformID

resolution.

### 2. Stateless GHL Marketplace OAuth callback

GHL Marketplace may call:

    /oauth/callback?code=<code>

without RVPay's `state`.

For this flow:

1. Require the authorization code.
2. Exchange the code with HighLevel.
3. Obtain the GHL `locationId`.
4. Resolve the specific pre-provisioned HighLevel integration using the existing deterministic mapping.
5. Obtain:
   - `integration.client_id`
   - `integration.platform_id`
6. Continue through the existing ProcessCallback flow.

NEVER:
- invent clientID
- invent platformID
- choose an arbitrary client
- choose the first HighLevel integration
- assume only one client exists
- convert/hash companyId/locationId into the RVPay client UUID

### 3. Existing Integration handling

`ProcessCallback` currently treats an already-existing integration as an error.

For this POC, if the resolved integration:

    status = CREATED

then reuse it instead of returning `ErrIntegrationAlreadyExists`.

Update it appropriately:

    status → ACTIVE
    external_account_id → GHL locationId

Then continue the existing token persistence/provider registration flow.

Do not weaken conflict handling for genuinely unrelated integrations.

### 4. GHL INSTALL webhook

The existing HighLevel INSTALL webhook handling is currently incomplete/stubbed.

Implement only what is necessary for the POC.

The INSTALL event contains information such as:

    companyId
    locationId
    appId
    companyName

Use `locationId` as the GHL sub-account identity.

Create or find the corresponding `payment_provider_configs` record:

    location_id = GHL locationId
    integration_id = resolved HighLevel integration ID

Behavior must be idempotent:

    config exists → reuse it
    config missing → create it

Do NOT create duplicate configurations.

Do NOT create a new RVPay Client from `companyId`.

Do NOT treat GHL `companyId` as an RVPay UUID.

### 5. Multiple-client safety

This is mandatory.

The code must continue to work when the database contains:

    Client A → HighLevel Integration A
    Client B → HighLevel Integration B

A GHL installation belonging to Client B MUST NOT resolve to Client A.

The lookup must use the GHL-specific identifier (`locationId`) or another existing deterministic mapping established during provisioning.

Add/adjust tests proving that the correct client is selected when multiple HighLevel integrations exist.

### 6. Event ordering

Do not assume that the OAuth callback and INSTALL webhook necessarily arrive in a particular order.

Make the relevant create/find operations idempotent.

If a required mapping/configuration does not yet exist, fail clearly rather than selecting an arbitrary client.

Do not introduce a new persistence mechanism just to solve ordering.

### 7. Database/schema constraints

NO migrations.

Use only the existing schema.

Do not add new database tables.

Do not add new columns.

Do not change the meaning of `clients.id`.

Do not hash GHL identifiers into RVPay UUIDs.

### 8. Tests

Update/add only the relevant tests.

Tests must cover:

1. Existing OAuth callback with `state`.
2. GHL OAuth callback with `code` and no `state`.
3. Stateless callback obtaining `locationId`.
4. Resolving the correct integration from the GHL location.
5. Resolving the correct client from that integration.
6. Existing CREATED integration being activated rather than returning `ErrIntegrationAlreadyExists`.
7. INSTALL webhook creating a missing payment_provider_config.
8. INSTALL webhook reusing an existing payment_provider_config.
9. Multiple HighLevel integrations/clients where the correct client is selected.
10. Missing location-to-integration mapping fails safely.
11. No fake/default client or platform IDs are generated.

Run all affected clients/OAuth/webhook tests and the normal Go test suite for affected packages.
