## Payment Checkout (paymentsUrl iframe) Facts

**FACT** — `/payment` is the RVPay checkout page loaded by HighLevel inside an iframe as the registered `paymentsUrl`. HighLevel supplies the transaction context via URL query parameters; the customer then selects country/provider/phone, and the page verifies the request against `POST https://api.rvpay.xyz/payments/custom-provider/query` (the Clients service `queryUrl` verify endpoint).
**FACT** — The provider `apiKey` is a server-side credential HighLevel delivers to `queryUrl`; it is NOT guaranteed on the `paymentsUrl`. The checkout page therefore requires only `transactionId` and forwards `apiKey`/`chargeId`/`subscriptionId` when present, and always sends `type: "verify"` to the query endpoint.
**FACT** — The backend query contract returns only success/failed/message (no order details), so order amount prefill is possible only from an `amount` URL parameter when HighLevel supplies one; otherwise the default amount remains editable.
**DECISION** — Checkout fixes stay inside `app/payment/page.tsx`; backend changes (exposing order details) are explicitly out of scope.

## Payment Checkout — postMessage Contract (verified against GHL docs §8.2)

**FACT** — HighLevel does NOT pass the payment context on the `paymentsUrl` query string. After the iframe posts a `ready` event to its parent, HighLevel sends a `payment_initiate_props` window message containing `publishableKey`, `amount`, `currency`, `mode`, `productDetails`, `contact` (id/name/email/contact/shippingAddress), `orderId`, `transactionId`, `subscriptionId`, `locationId`. The iframe must start the payment flow on receipt of this event.
**FACT** — The checkout page implements the handshake: posts `{type:"ready"}` to `window.parent` on mount (target origin `*`, non-secret marker only), listens for `payment_initiate_props`, and merges the event with URL params (event primary, URL fallback).
**FACT** — Order prefill comes from the event: `amount` (locked), `currency` → country preselection (unambiguous ISO codes only; XOF/XAF/FCFA not mapped — multi-country), `contact.contact` → phone with dial code stripped.
**DECISION** — The event payload is never transmitted anywhere; verification still goes through `POST /payments/custom-provider/query` (`type: "verify"`, event `transactionId`, plus `orderId`/`subscriptionId` when present). No completion postMessage back to HighLevel exists yet — pending the documented completion contract.

## Agent 00-payment-page-agent — transactionId Authority + Real Initiation (supersedes the postMessage section above)

**FACT** — `payment_initiate_props` is SUSPENDED: live console evidence shows HighLevel never sends it after the `custom_provider_ready` post. The listener and `[RVPay]` diagnostics are retained for future reactivation, but nothing in the payment flow depends on it. Missing `payment_initiate_props` never blocks payment.
**FACT** — The authoritative `transactionId` is read from the payment URL query string (`URLSearchParams(window.location.search)` behind a `typeof window` guard; SSR-safe). Fallback order: URL → suspended event → fail safely with "Invalid payment request. Missing payment transaction information." No ID is generated or fabricated client-side.
**FACT** — Pay now calls the EXISTING Transactions grpc-gateway initiation endpoint `POST /v1/public/deposits` (`CreateDepositRequest`: `amount{amount,currency}`, `paymentType: "PAYMENT_TYPE_MMO"`, `payerPhoneNumber` = dial code + phone, `provider` = `PROVIDER_MTN_MOMO`/`PROVIDER_ORANGE_MOMO`; `clientId`/`customerId`/`merchantId` forwarded only when present on the URL). Status polling uses the EXISTING `GET /v1/public/payments/verify` (`VerifyPayment`) with the same `ghlTransactionId`.
**FACT** — Duplicate prevention: `isSubmitting` state + disabled button while processing; single polling interval, cleaned up on unmount/terminal state.
**KNOWN GAP (backend change required — explicitly out of scope, operator forbidden backend edits)** — `CreateDepositRequest` has no `ghl_transaction_id` field, so initiated deposits cannot be correlated to the HighLevel transaction that `VerifyPayment` looks up (column/index exist via migration 000002 but nothing persists the value). Full end-to-end correlation therefore requires an approved backend change; until then the page correctly surfaces backend errors instead of fabricating context.

## Surgical Correction — transactionId Semantics (latest, supersedes the transactionId priority above)

**FACT** — A later edit of the page mapped `buyNowProductId` to `transactionId`; that was a semantic mistake and has been removed. `transactionId` is now read ONLY from a genuine `transactionId` URL param or the suspended `payment_initiate_props` event, and is `null` when neither is present.
**FACT** — The `if (!transactionId)` gate was removed from `handlePay`: payment initiation (`POST /v1/public/deposits`) is independent of the GHL transaction id. Form validation covers terms, phone, positive amount, and provider support.
**FACT** — GHL-specific verification (`GET /v1/public/payments/verify`) runs ONLY when a real `transactionId` exists; otherwise the page reports an honest "submitted — status tracking unavailable until correlation is configured" and does NOT poll or fake success. A deposit `id` returned by the backend is retained/logged, but HTTP 200 is never presented as payment success.
**FACT** — Secrets are not copied into the image: `.dockerignore` excludes `**/.env`, `**/.env.*`, and `*.pem`; the Dockerfile COPYs only `package.json`, `package-lock.json`, `node_modules`, the build source, and the standalone runtime output. Agent 03 confirmed `.env*`, `*.pem`, `*.key` absent from the built image.
**FACT** — Container startup check (Agent 04): `docker run rvpay/admin:agent03` with no application env vars started the Next.js 16.3.0 standalone server and returned HTTP `200` on `/`. Startup log shows `✓ Ready` with no missing-configuration errors. The only passed var, `NODE_ENV=production`, is redundant with the baked-in value.
