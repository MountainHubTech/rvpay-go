# Dashboard Setup — RVPAY Admin Dashboard (`admindashboard/`)

This document explains exactly how the dashboard works today: every page, every
piece of static (hardcoded) data, and precisely what a server must return to
replace that data with live information. After reading it, anyone should know
how each page will communicate with a backend and in what shape the backend
must answer.

---

### Shared chrome

- `layout.tsx` — Geist + Geist Mono fonts, metadata "RVPAY — Payments Monitor".
- `components/dashboard/app-sidebar.tsx` — all six nav items are now linked:
  Dashboard (`/`), Sub-Accounts (`/sub-accounts`), Transactions
  (`/transactions`), Payouts (`/payouts`), Disputes & Errors (`/disputes`),
  Settings (`/settings`). Transactions/Disputes/Settings are placeholder
  pages (see §2.7). Footer still shows a hardcoded user: `Admin User` /
  `admin@rvpay.com` — a server must supply the authenticated identity here
  (`GET /me` style endpoint: `{ name, email, avatarUrl }`).
- `components/dashboard/topbar.tsx` — global "Search sub-accounts" input and a
  notification bell; both are inert. A server would back these with a
  sub-account search endpoint and a notifications endpoint.
- `components/dashboard/period-select.tsx` — now a **controlled** dropdown:
  `PeriodSelect({ value, onChange })` with options typed as `DashboardPeriod`
  (`"Last 7 Days" | "Last 30 Days" | "Last 90 Days" | "This Year"`). It no
  longer holds its own state; `DashboardHome` owns the period and passes it
  down. It still does **not** trigger any network fetch — see §2.1.

### The static-data hub

`lib/dashboard-data.ts` is the single module all dashboard data comes from.
It still contains the same typed static constants:

- `statCards: StatCard[]` (4 cards)
- `revenueOverTime` (7 weekly buckets)
- `needsAttention: AttentionItem[]` (3 items)
- `recentPayouts: Payout[]` (5 rows)
- `subAccounts: SubAccount[]` (4 rows)
- `payoutOverviewStats: PayoutOverviewStat[]` (3 cards)
- `payoutOverviewRows: PayoutOverviewRow[]` (4 rows)

Newly added, the snapshot layer that the dashboard home consumes:

```ts
export type DashboardPeriod = "Last 7 Days" | "Last 30 Days" | "Last 90 Days" | "This Year"

export type DashboardSnapshot = {
  statCards: StatCard[]
  revenueOverTime: typeof revenueOverTime
  needsAttention: AttentionItem[]
  recentPayouts: Payout[]
}

export function getDashboardSnapshot(_period: DashboardPeriod): DashboardSnapshot
```

**`getDashboardSnapshot` currently ignores its period argument** and returns
the identical static snapshot for all four periods — this is the seam where a
server call belongs.

### The data-flow pattern (props, not imports)

The dashboard was refactored so widgets receive data via props instead of
importing constants directly:

| Component | New props |
|---|---|
| `DashboardHome` (client) | `{ initialSnapshot: DashboardSnapshot }` |
| `StatCards` | `{ cards: StatCard[] }` |
| `RevenueChart` | `{ data: DashboardSnapshot["revenueOverTime"] }` |
| `NeedsAttention` | `{ items: AttentionItem[] }` |
| `RecentPayouts` | `{ payouts: Payout[] }` |
| `SubAccountsTable` | `{ accounts?: SubAccount[] }` (defaults to static `subAccounts`) |
| `PayoutsOverview` | `{ rows?: PayoutOverviewRow[] }` (defaults to static `payoutOverviewRows`; stats still imported directly) |
| `PlaceholderPage` | `{ title, description }` (pure presentational) |

**Server replacement pattern:** replace `getDashboardSnapshot(_period)` with a
fetch to `GET /overview/snapshot?period=...` (server-side in `app/page.tsx`
for the initial render, client-side on period change). The `DashboardSnapshot`
type is exactly the response shape the server must return.

## 2. Page-by-Page Specification

### 2.1 `/` — Dashboard Overview (`app/page.tsx` → `components/dashboard/dashboard-home.tsx`)

`app/page.tsx` (server component) calls `getDashboardSnapshot("Last 7 Days")`
and passes it as `initialSnapshot` to `DashboardHome`, a **client component**
that owns the `period` state. On period change it calls
`getDashboardSnapshot(period)` **synchronously** (no network — all four
periods return the same static data today). The chosen period is passed to
`PeriodSelect({ value, onChange })`, and snapshot fields are passed down as
props: `StatCards cards`, `RevenueChart data`, `NeedsAttention items`,
`RecentPayouts payouts`.

**Server replacement (single clean seam):** make `getDashboardSnapshot(period)`
async/fetch-based, or fetch in `app/page.tsx` for SSR and refetch on change:

```
GET /api/v1/overview/snapshot?period=Last 7 Days|Last 30 Days|Last 90 Days|This Year
→ { statCards: StatCard[], revenueOverTime: [{ period: string, revenue: number }],
    needsAttention: AttentionItem[], recentPayouts: Payout[] }
```
i.e. exactly the `DashboardSnapshot` type. The per-widget contracts below
still describe what each field must contain.

### 2.5 `/payment` — HighLevel Checkout (`app/payment/page.tsx`)

The only page with live server communication. `"use client"` page loaded by
HighLevel as the registered `paymentsUrl` inside an iframe. Flow:

1. **Handshake (postMessage, no server):**
   - Registers a `window.addEventListener("message", ...)` listener **before**
     posting the ready event.
   - Posts `JSON.stringify({ type: "custom_provider_ready", loaded: true,
     addCardOnFileSupported: false })` to `window.parent`, retried every
     **500ms** until the payment context arrives or unmount.
   - Accepts `payment_initiate_props` **and** `setup_initiate_props` events;
     `event.data` may be a JSON string or an object (safe `JSON.parse`,
     malformed ignored). Payload type `PaymentInitiateProps`: `type`,
     `publishableKey`, `amount`, `currency`, `mode`, `productDetails`,
     `contact { id, name, email, contact, shippingAddress }`, `orderId`,
     `transactionId`, `subscriptionId`, `locationId`.
   - Prefills from the event: `amount`, currency → country via
     `CURRENCY_COUNTRY` map (unambiguous ISO codes only; FCFA/XOF/XAF not
     mapped), customer phone (dial code stripped).
   - Extensive `[RVPay]` console diagnostics retained.

2. **Static data on this page (not server-fetched today):**
   - `PROVIDERS` map — 16 pawaPay mobile-money providers with brand colors:
     `mtn` (pill), `orange`, `moov`, `wave`, `airtel`, `vodacom`, `mpesa`,
     `at`, `vodafone`, `tnm`, `movitel`, `free`, `zamtel`, `tigo`, `halotel`,
     `safaricom`.
   - `COUNTRIES` — 20 supported countries (BJ, BF, CM, CI, CD, ET, GA, GH, KE,
     LS, MW, MZ, NG, CG, RW, SN, SL, TZ, UG, ZM), each with flag emoji, dial
     code, display currency and provider list (e.g. GH → GHS → mtn/at/
     vodafone).
   - **Server replacement:** a provider-availability endpoint so the lists
     become dynamic:
     ```
     GET /api/v1/payment/providers?country=GH
     → [ { id: string, name: string, bg: string, fg: string,
           shape?: "pill"|"square" } ]
        // plus per-country availability/currency, sourced from pawaPay
     ```
   - URL query params also read (fallback to the event): `type`,
     `transactionId`, `apiKey`, `chargeId`, `subscriptionId`, `amount`.
     `buyNowProductId` is deliberately NOT treated as a transactionId.

3. **Pay → initiation (server call #1):**
   `POST https://api.rvpay.xyz/v1/public/deposits` (Transactions service,
   grpc-gateway, `CreateDepositRequest`). Body mapping:
   - `clientName = "highlevel-<locationId>"` (backend convention)
   - `customerId = initiateProps.contact.id`
   - `merchantId = payer phone number` (current temporary requirement — NOT
     the HighLevel transactionId)
   - `ghlTransactionId = genuine HighLevel transactionId` (persisted in
     `deposits.ghl_transaction_id` for verify lookups)
   - `amount` (validated positive number), `currency` via `currencyToApi`
     (`FCFA` → `XAF`, else uppercase ISO), `paymentType`,
     `payerPhoneNumber`, `provider` via `providerToApi` — only `mtn` →
     `PROVIDER_MTN_MOMO` and `orange` → `PROVIDER_ORANGE_MOMO` are supported;
     other selections are rejected client-side with "This mobile money
     provider is not supported yet. Please select MTN or Orange Money."
   - Fail-safes before calling: missing `locationId` → "Missing payment
     location information"; missing `contact.id` → "Missing payment contact
     information"; missing `transactionId` → "Missing payment transaction
     information". Terms checkbox + phone + positive amount required to
     enable Pay.
   - Expected success response: the created deposit record (the page retains/
     logs the backend deposit `id`); HTTP 200 is **never** shown as payment
     success.

4. **Status polling (server call #2):**
   `GET https://api.rvpay.xyz/v1/public/payments/verify?ghlTransactionId=...
   [&ghlChargeId=...][&subscriptionId=...]` → `QueryResponse
   { success?: boolean; failed?: boolean; message?: string }`.
   - Polls every **3000ms** (`PAYMENT_POLL_INTERVAL_MS`), single interval.
   - Terminal success: `success === true` → "Payment completed" modal (green ✓).
   - Terminal failure: `failed === true` → "Payment failed" modal (red ✕).
   - Both false → keep polling; transport/server errors logged (`console.warn`)
     and retried inside the window.
   - Hard timeout after **10 minutes** (`PAYMENT_POLL_TIMEOUT_MS`) → timeout
     message, polling stops, result modal NOT shown.
   - Timers cleared on terminal state and unmount; duplicate submissions
     blocked by `isSubmitting`.
   - Modal "OK" dismisses only — no HighLevel return URL exists in the
     integration (documented safe seam for a future `returnTo`).

## 3. Summary — What a Backend Must Provide

### LIVE endpoints (implemented and verified as of 2026-09-04)

These are served by the Transactions service and consumed by the current
dashboard source:

| # | Method | Path | Page | Status |
|---|---|---|---|---|
| 1 | `POST` | `/v1/public/deposits` | `/payment` | **LIVE** |
| 2 | `GET` | `/v1/public/payments/verify?ghlTransactionId=&ghlChargeId=&subscriptionId=` | `/payment` | **LIVE** |

**CreateDepositRequest body (the contract the dashboard sends):**
```json
{
  "clientName": "highlevel-<locationId>",
  "customerId": "<payment_initiate_props.contact.id>",
  "customer": {
    "name": "<contact.name or \"\">",
    "phoneNumber": "<country.dialCode><phone>",
    "address": "<collapsed shippingAddress or \"\">"
  },
  "merchantId": "<payer phone number>",
  "ghlTransactionId": "<genuine HighLevel transactionId>",
  "amount": { "amount": "<decimal string>", "currency": "XAF" },
  "paymentType": "PAYMENT_TYPE_MMO",
  "payerPhoneNumber": "<country.dialCode><phone>",
  "provider": "PROVIDER_MTN_MOMO | PROVIDER_ORANGE_MOMO"
}
```
Mappings: `mtn -> PROVIDER_MTN_MOMO`, `orange -> PROVIDER_ORANGE_MOMO`,
`FCFA -> XAF`. The `customer` object is created/resolved inside the same
database transaction as the deposit and PawaPay initiation. `buyNowProductId`
is **not** used as a transaction ID; no identifiers are fabricated.

**VerifyPaymentResponse:** `{ "success": boolean, "failed": boolean }`
(polling keeps `GET`; terminal state = `success===true` or `failed===true`).

### Cross-cutting

- Return shapes matching the TypeScript types in `lib/dashboard-data.ts`.
- The `PeriodSelect` period must be plumbed through overview endpoints.
- **No auth on any route today.** `/me` and any privileged `/api/v1/*`
  endpoints are blocked on an authentication decision — none exists
  client-side.
- API base URL is hardcoded to `https://api.rvpay.xyz` in
  `app/payment/page.tsx`; new fetches should follow the same convention.
