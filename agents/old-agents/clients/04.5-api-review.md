# Agent 04.5 — API Architecture Review

## Objective

Perform a comprehensive architectural review of the Clients Service API before implementation begins.

This agent exists to validate the public contract.

Its purpose is to ensure the generated protobuf definitions represent a clean, stable, scalable API suitable for long-term evolution.

No business logic should be implemented during this task.

No repositories should be implemented during this task.

No runtime code should be implemented during this task.

Only improve the API contract where necessary.

The API should be considered frozen once this review is complete.

# Review Goals

Assume the protobufs are about to become public.

Review them as though external developers will depend upon them permanently.

Identify opportunities to improve:

clarity

consistency

extensibility

backward compatibility

discoverability

developer experience

Do not introduce unnecessary complexity.

# Service Boundary Review

Verify every RPC belongs to the correct service.

Confirm responsibilities remain clearly separated.

ClientsService should own:

Client lifecycle

PlatformService should own:

Provider catalogue

IntegrationsService should own:

Provider installations

OAuth

Webhook registration

Move RPCs only if architecture requires it.

---

# RPC Review

Review every RPC.

Confirm:

name is clear

verb is appropriate

request is minimal

response is meaningful

RPC purpose is obvious

Avoid ambiguous names.

Prefer business terminology.

Avoid implementation terminology.

---

# REST Review

Review grpc-gateway mappings.

Verify:

HTTP verb

resource path

path parameters

query parameters

resource hierarchy

Avoid RPC-style endpoints.

Prefer RESTful resources.

Examples:

/clients

/clients/{id}

/clients/{id}/integrations

/platforms

/integrations

Ensure naming remains consistent.

---

# Message Review

Inspect every message.

Verify:

field names

field ordering

required information

future extensibility

message reuse

Avoid duplicate messages.

Avoid giant request messages.

Avoid deeply nested objects.

---

# Enum Review

Review every enum.

Confirm:

clear naming

consistent prefixes

future extensibility

no duplicated concepts

Reserve future values where appropriate.

---

# Field Number Review

Verify protobuf numbering.

Ensure:

no reused numbers

deleted numbers reserved

logical ordering

room for expansion

Never renumber existing fields.

# Shared Objects Review

implementation details

The protobuf contract should require only additive changes going forward.

---

# Completion Rules

Before completing verify:

- Existing protobuf conventions have been preserved.

- Existing package naming has been been preserved.

- Existing generation workflow has been preserved.

- Existing grpc-gateway conventions have been preserved.

- Existing Makefile conventions have been preserved.

- Generated files have not been manually edited.

- No unrelated directories were modified.

- The project builds successfully.

If any issue prevents approving the API contract, stop and explain the blocker instead of proceeding to repository implementation.

# Approval Gate

If the API review results in architectural changes larger than approximately 10% of the generated protobuf definitions, stop after updating the protobufs and regenerating code.

Do not continue to downstream implementation.

The API must stabilize before repository implementation begins.

If only minor improvements are required (comments, naming consistency, message reuse, HTTP path refinements, reserved fields, etc.), complete those improvements within this agent.

This review is considered the final approval step before repository implementation.
