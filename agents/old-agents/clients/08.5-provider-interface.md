# Unified Provider Architecture

Before implementing runtime wiring, review the provider implementation created by Agents 07 and 08.

The Clients service should expose a unified provider abstraction.

If separate OAuth and Webhook implementations exist for a provider, consolidate them behind a single Provider implementation where appropriate.

The preferred architecture is:

Provider

↓

OAuthProvider

↓

WebhookProvider

Every concrete provider should satisfy the complete Provider contract.

Example:

HighLevelProvider

implements

- Provider
- OAuthProvider
- WebhookProvider

Future providers should follow the same pattern.

Examples include:

- HubSpot
- Salesforce
- Zoho CRM
- Pipedrive
- Monday.com

Do not implement these providers.

Design the architecture so they can be added without modifying existing business services.

---

# Provider Registry

Implement a Provider Registry responsible for discovering and supplying provider implementations.

The registry should:

- register providers

- retrieve providers by identifier

- expose provider capabilities

- prevent duplicate registrations

The remainder of the Clients service should communicate only with the Provider interface.

Avoid provider-specific branching throughout the application.

Never introduce code such as:

if provider == "highlevel"

or

switch provider

outside the Provider Registry.

The registry becomes the single source of truth for provider discovery.

---

# Provider Capabilities

Every Provider should expose its capabilities.

Capabilities may include:

- OAuth

- Webhooks

- Token Refresh

- Installation

- Uninstallation

- Health Checks

Business services should query provider capabilities rather than making assumptions.

Future providers may implement only a subset of capabilities.

The Provider interface should allow capability discovery without requiring type assertions.

---

# Dependency Rules

The remainder of the Clients service should depend only on:

Provider

Never depend directly on:

HighLevelProvider

HubSpotProvider

SalesforceProvider

or any future concrete implementation.

Concrete providers should only be referenced during Provider Registry registration.

This keeps the remainder of the service completely provider agnostic.

---

# Validation

Before completing verify:

- every provider implements the Provider interface

- OAuth functionality remains operational

- webhook functionality remains operational

- provider registration succeeds

- business services depend only on Provider

- no provider-specific branching remains outside the registry

- future providers can be added by implementing Provider and registering them

If the Provider abstraction requires only internal refactoring, perform the refactoring.

If implementing the abstraction would require redesigning previous agents, stop and document the architectural issue instead.
