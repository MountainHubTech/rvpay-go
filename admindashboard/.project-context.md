### Final Environment Model (verified by Agent 04)

**FACT** — Verified by targeted grep over `app/`, `lib/`, and `components/` (all `.ts`, `.tsx`, `.js`, `.mjs`, `.cjs`): zero `process.env` and zero `NEXT_PUBLIC_*` references. This independently reconfirms Agent 01 and closes the Task 4 reading map.
**FACT** — By classification, the variable inventory is empty:
  - **public/client (`NEXT_PUBLIC_*`):** none
  - **server/runtime:** none (the only runtime value is `NODE_ENV=production`, which is baked into the image in the Dockerfile `ENV` step, not supplied at container runtime)
  - **build-time-sensitive:** none
**DECISION** — No `.env.example` is added. Task 4 permits an example environment file only "if justified by actual variables"; with zero variables such a file would be an invented, misleading artifact. This decision is recorded and later agents must not add one.
**DECISION** — The zero-env baseline is the default container contract. If a future variable becomes necessary, it is supplied at container runtime via `docker run -e KEY=value` or `docker run --env-file`, and must never be written into the image or converted into `NEXT_PUBLIC_*`.
**FACT** — Secrets are not copied into the image: `.dockerignore` excludes `**/.env`, `**/.env.*`, and `*.pem`; the Dockerfile COPYs only `package.json`, `package-lock.json`, `node_modules`, the build source, and the standalone runtime output. Agent 03 confirmed `.env*`, `*.pem`, `*.key` absent from the built image.
**FACT** — Container startup check (Agent 04): `docker run rvpay/admin:agent03` with no application env vars started the Next.js 16.3.0 standalone server and returned HTTP `200` on `/`. Startup log shows `✓ Ready` with no missing-configuration errors. The only passed var, `NODE_ENV=production`, is redundant with the baked-in value.

## Docker Constraints

**DECISION** — Dockerization is the goal; modernization is not.
**DECISION** — The production image must be the smallest practical multi-stage build.
**DECISION** — No secrets may be copied into the image.
**DECISION** — No Docker files are created in Agent 00.
**FACT** — A standard multi-stage Next.js image is suitable; nothing in the application makes it unsuitable.
**FACT** — `next/font/google` requires network access during the build stage of the Docker image.
**DECISION** — Agent 03 finalized the Dockerfile as a three-stage build: `deps` (`npm ci` from the committed lockfile) → `builder` (`next build`) → `runner` (minimal standalone runtime).
**DECISION** — Runner base image is `node:22-alpine` (Node 22 stable LTS, compatible with Next.js 16). Build tooling is isolated; no `node_modules` install or source tree is copied into the runtime.
**DECISION** — Runtime entrypoint is `node server.js` (the Next.js standalone server), run as unprivileged user `nodejs` (uid/gid 1001). The `next` CLI is not on `PATH`, so `CMD ["next","start"]` is invalid for this image.
**DECISION** — Standalone output and `public/` are copied to `/app` root; `.next/static` is placed at `/app/.next/static` (the standalone server's expected paths).
**DECISION** — Container listens on port 3000 (Next.js standalone default).
